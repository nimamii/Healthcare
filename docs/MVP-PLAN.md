## ۳. مسیر بحرانی

```
فاز ۲  ──►  فاز ۳  ──►  فاز ۴  ──►  فاز ۵
Catalog     Inventory   Fulfillment  Commerce
```

این چهار فاز مسیر واقعی «اولین سفارش» هستند. فاز ۱ زیرساخت این مسیر است. فاز ۷ و ۸ **بعد** از این مسیر می‌آیند — حتی اگر در زمان‌بندی موازی باشند.

هیچ فازی نباید مسیر بحرانی را به تأخیر بیندازد. اگر تعارض بود، مسیر بحرانی اولویت دارد.

## ۴. وابستگی‌ها

| این | به این وابسته است |
|---|---|
| Inventory | Catalog (شناسه محصول/SKU) |
| Fulfillment | Inventory + Geography + Suppliers |
| Orders | Fulfillment + Catalog + Customers |
| Payments | Orders |
| Fulfillment Engine | Inventory model نهایی‌شده |

**نکته:** Fulfillment به هر سه ماژول وابسته است. اگر مدل موجودی زود نهایی نشود، فاز ۴ عقب می‌افتد. بنابراین **مدل موجودی اولین خروجی قابل‌تحویل فاز ۳ است**، نه آخرین.

## ۵. ریسک‌ها

| ریسک | احتمال | اثر | کاهش |
|---|---|---|---|
| **یکپارچه‌سازی ERP تأمین‌کننده مبهم است** | بالا | بالا | Adapter + mock. هرگز منتظر API واقعی نمان (§5) |
| **API لجستیک/پرداخت در دسترس نباشد** | متوسط | متوسط | Interface + mock از روز اول (§11, §26) |
| **Over-engineering** | بالا | بالا | قانون MVP FIRST. هر abstraction بدون provider واقعی = بی‌فایده |
| **تعارض ERP با مدل داخلی** | متوسط | متوسط | normalization لایه مشترک؛ نه per-supplier |
| **Overselling در موجودی** | کم | **بسیار بالا** | transaction + row-level lock + تست (§6, §39) |
| **تأخیر پروژه** | متوسط | بالا | فاز ۶ از قبل حذف شده. بیشتر نمی‌توان حذف کرد |
| **مقاومت تأمین‌کننده در یکپارچه‌سازی** | متوسط | بالا | CSV fallback. تأمین‌کننده نباید نرم‌افزارش را عوض کند (§4) |

## ۷. تعریف انجام‌شدن (§36)

یک قابلیت وقتی انجام‌شده است که:

- پیاده‌سازی هست
- **اعتبارسنجی** هست
- **Authorization درست** هست
- **تست** هست و پاس می‌شود
- مدیریت خطا هست
- مستندات به‌روز شده
- در **جریان واقعی کاربر** کار می‌کند

«کد نوشته شد» ≠ «انجام شد».
